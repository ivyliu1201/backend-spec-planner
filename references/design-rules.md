# 設計準則

依確認行為設計，沿用既有架構；變更授權見 [SKILL.md](../SKILL.md)。

## 責任邊界

- 依業務責任與變更原因劃分模組。
- 標明規則擁有者、資料修改權、公開操作、依賴及失敗決定者。
- 規則由主要擁有者維護，跨模組修改資料須經約定操作。
- 檢查重複規則、循環依賴及跨界修改。
- 以本次規則變更推演修改位置及受影響契約。
- 區分業務判斷、流程協調與技術操作；程式分層及部署方式依需求決定。

## 互動與契約

- 正常及重要失敗路徑須能定位呼叫者、操作、資料來源、結果用途與後續責任。
- 每項狀態變更及副作用須有具體操作與契約支持；必要能力缺失時先釐清。
- 交易須說明原子範圍、提交、可見時機及失敗保留／回滾範圍。
- 重複、並行或中斷會影響結果時，定義識別、衝突結果及恢復責任；批次細節見 [batch-processing.md](batch-processing.md)。
- 新增操作明確定義必要契約，區分規格與既有實作。

## 模組選用

- 先讀能力目錄，辨識協作或替代關係，再讀選定操作的契約；不符時回查候選。無目錄則查相關來源。
- **協作**：定義交接資料、順序、回應及後續決定者。
- **替代**：定義資格、優先順序、條件來源及選擇責任。
- **候選數量**：明定零個、一個及多個符合者的結果；缺少選用依據時先確認。
- **失敗切換**：另定可切換條件與副作用防重。

## 方法選用

- 簡單功能優先沿用既有元件，採直接實作。
- DDD（領域驅動設計）按複雜業務模型需要選用。
- 術語有歧義時釐清適用邊界；資料須共同維護條件時評估一致性邊界。
- 模型只描述必要的身分、生命週期、有效值、單位、精度與一致性。
- 設計模式依具體變化或耦合問題選用，比較直接實作與既有元件，說明收益、代價及限制。
- 新抽象須有現行需求或約束支持。
- 交易、冪等及撤銷等保證以契約為準。

## 效能與容量

- 效能影響設計時，確認資料量、併發、頻率、耗時及資源限制。
- 依負載檢查逐筆查詢／遠端呼叫、整批載入、重複計算、過長交易及資源競爭。
- 最佳化依瓶頸證據選用，保留正確性、權限、順序、一致性及防重要求。
- 量測須有入口、資料、環境、指標與門檻；必要條件缺失時先確認，基準比較採相同條件。
- 評估效能收益與維護成本；增加複雜度須有瓶頸或新要求支持。
