# backend-spec-planner 評估案例

僅供維護評估，案例判準不加入一般任務流程。

驗證指令見[驗證指南](verification.md)；執行結果見[改版驗證](redesign-results.md)與[歷史紀錄](history.md)。

## 評估方式

- 在隔離對話或暫存專案執行；只提供測試輸入與素材，判準由評估者保留。
- 產出或修訂規格的案例明確呼叫 `$backend-spec-planner`；案例 10 測實際選用入口，案例 17 只做讀者理解測試。需要檔案的案例只建立所列最小材料；案例中的檔名是測試資料，不是本 Skill 的必要檔案。
- 依實際回覆、讀取範圍及產物判分，記錄輸入、證據、結果與原因。
- 缺少執行證據標「未驗證」；靜態檢查、作者走讀與獨立測試分開記錄。
- 案例 10 必須經過 Codex 的實際 Skill 選用入口；把 SKILL.md 強制注入對話，無法驗證「不隱含觸發」。

## 01：無模板建規格

**測試輸入**

> $backend-spec-planner 請替「已登入的企業使用者查詢自己提交的批次處理結果」建立規格草案。已確認只能看所屬企業資料，可取得目前狀態及成功、失敗筆數。專案沒有既有模板；狀態名稱和查詢介面尚未決定。先交付草案，不寫程式。

**預期行為**

- Given 沒有模板，When 建立草案，Then 以一份 Feature Spec 描述目的、行為、已知責任與具體 BDD；有用途才展開設計，未知事項明列缺口。
- 清楚區分已確認的企業資料隔離規則與未決狀態／介面；提出推薦，優先核對會改變結果的問題。
- 只建立有實際用途的文件。

**失敗判準**

- 要求先交付認可模板才工作。
- 為湊章節新增政策或留下空欄。
- 把未知當不適用。
- 自行指定狀態為已確認。
- 固定產出五份文件。
- 直接實作 API。


## 02：需求與技術約束

**測試輸入**

> $backend-spec-planner 幫我建立銀行批次規格，目前只知道「必須使用 Upload API」，尚無 API 文件。

**預期行為**

- Given 只有技術限制，When 分析規格，Then 將 Upload API 歸為約束，指出缺少業務目的、受理／完成條件及操作契約。
- 先簡述推薦方向、理由與影響，再只問最影響結果的一個問題；未收到回答前不產出規格框架、草案或正式文件。
- 後續逐題釐清必要決策；可先查找契約，不問已回答的問題或等價內部寫法。
- 區分上傳、受理與處理完成。

**失敗判準**

- 把「呼叫 Upload API」當完整業務需求。
- 捏造端點、參數或 HTTP 回應。
- 認定上傳成功即批次完成。
- 一輪同時問用途、完成條件與契約等多個問題。
- 以一個問號包裝多項獨立決策。
- 必要資訊仍缺就先交帶空欄的規格。


## 03：模組協作

**測試輸入**

> $backend-spec-planner 依模組目錄設計已確認的薪轉檔案處理功能：上傳 CSV 後交給支援 CSV 的解析能力，解析結果再做業務驗證。先說明使用哪些模組與責任。
>
> 目錄：A 負責檔案接收並回傳檔案識別，契約在 a-contract.md；B 提供 CSV 解析，契約在 b-contract.md；C 提供固定長度檔解析，契約在 c-contract.md。B／C 不執行業務驗證。各契約篇幅很長，目錄資訊已確認。

**預期行為**

- Given A 與解析能力分工，When 分析 CSV 情境，Then 將 A 與 B 視為協作、B／C 視為同類能力替代。
- 先由目錄判斷協作／替代、選定 A／B 的接收與解析操作，再讀必要契約；沒有新證據需求不讀 C 的完整內部細節。
- 指出業務驗證責任仍未指定，提出合理建議並等待確認，不把責任塞入 B。

**失敗判準**

- 在 A／B／C 三者中只選一個。
- 先讀遍三個模組全部實作。
- 忽略業務驗證的責任缺口。
- 自行讓 B 負責業務驗證。


## 04：重試與副作用

**測試輸入**

> $backend-spec-planner 審查以下規格，不修改檔案：「批次逐筆呼叫外部扣款；失敗後重試，直到成功。」外部系統可能扣款成功後回應逾時，目前沒有提供冪等或查詢契約。

**預期行為**

- Given 可能已扣款但回應逾時，When 審查重試，Then 指出重複扣款與結果不明風險。
- 釐清可重試條件、操作身分、防重／查詢能力、停止條件與耗盡結果；推薦查明外部結果再決定重試。
- 不自行指定次數或宣稱外部支援冪等；維持只審查。

**失敗判準**

- 直接建議無限重試或固定三次。
- 認為本地回滾即可撤銷扣款。
- 修改檔案。
- 宣稱 exactly-once 已獲保證。


## 05：領域模型

**測試輸入**

> $backend-spec-planner 請為以下已確認需求提出 DDD 設計草案：一個提交批次有多筆付款項目，受理後原始內容不能改；每筆付款各有結果，批次彙總必須可核對。檔案可能很大。既有接收模組只負責儲存檔案。

**預期行為**

- Given 已知不變條件，When 設計領域責任，Then 指明誰維護受理後不可修改、逐筆結果及彙總核對。
- 依一致性需求討論批次、付款項目及金額概念，說明聚合候選與大檔限制，標示建議及未知交易邊界。
- 區分應用協調、領域規則與技術檔案儲存，保留接收模組的已確認責任。

**失敗判準**

- 只列 Controller／Service／Repository 或 DDD 名詞。
- 每個處理步驟切一個微服務。
- 強制整檔載入同一聚合。
- 把受理規則直接交給接收模組。


## 06：抽象必要性

**測試輸入**

> $backend-spec-planner 請優化這個技術設計。需求只支援一種 CSV 格式與一個既有解析器，沒有其他格式需求。現在設計打算新增 ParserFactory、ParserRegistry 與外掛介面，理由是未來可能擴充。這些只是未採用草案。

**預期行為**

- Given 只有單一實作且尚未確認抽象，When 優化草案，Then 建議直接使用既有解析器，說明額外抽象目前沒有對應問題。
- 保留重要輸入、錯誤及責任契約；不因拿掉模式而改業務行為。

**失敗判準**

- 強制保留／增加工廠模式以符合 DDD。
- 新增外掛設定或未知格式需求。
- 刪除必要錯誤含義。


## 07：規格與實作差異

**測試輸入**

> $backend-spec-planner 逆向整理重複提交的規格。文件 docs/submit.md 寫「重複批次應拒絕」。程式 SubmitHandler.submit 的現況是遇到相同業務鍵就回傳舊結果；對應測試也如此。文件的確認紀錄與變更背景目前找不到。不要修改程式。

**預期行為**

- Given 文件與實作不同，When 逆向分析，Then 分別記錄既有記載與實作／測試證據，說明拒絕與回傳舊結果的差異。
- 在對話說明推薦與需要的決策；可以整理實作現況，但不能把任一方當作業務政策。

**失敗判準**

- 直接宣布程式或文件必然正確。
- 改寫文件抹平衝突。
- 修改程式或測試。
- 把既有測試當需求確認。

## 09：規格完整性

>

## 12：契約分流

**測試輸入**

> A：$backend-spec-planner 請補模組使用規格。api/upload.yaml 的 v1 uploadFile 已完整定義 submitId（必填 UUID）、content（必填二進位）、成功回傳 fileId，以及格式錯誤和權限不足的結果。已確認額外規則：「相同提交識別不得搭配不同檔案內容」尚未寫入使用說明，衝突的對外結果未定義。這次只補說明，不改 API。
>
> B（另一個新對話）：$backend-spec-planner FileReceiver 目前沒有足夠操作契約。請依已確認需求提出 Module Contract 草案：接收提交識別與檔案內容，保存後回傳檔案識別；相同識別與內容重送須回舊結果且不重存，相同識別但不同內容須拒絕且不覆寫。具體型別、錯誤識別、並行保障與防重期限未確認。只提介面草案，不修改程式。

A 的原始檔案 `api/upload.yaml` 如下（測試用契約格式，非 OpenAPI 文件）：

```yaml
version: v1
operations:
  uploadFile:
    purpose: 保存檔案供後續批次受理使用
    precondition: 呼叫者具備 file:write 權限
    input:
      submitId: {type: string, format: uuid, required: true}
      content: {type: binary, required: true}
    success:
      fileId: {type: string, format: uuid, required: true}
      meaning: 檔案已保存，不代表批次受理或處理完成
    errors:
      InvalidInput: 輸入格式不符，未保存檔案
      Forbidden: 權限不足，未保存檔案
```

**預期行為**

- Given 欄位定義已有權威來源，When 補契約使用規格，Then 引用 uploadFile 與版本／位置，只補已確認的使用限制與必要行為缺口。
- A 的衝突結果尚未定義，先在對話釐清該結果，不猜錯誤碼或直接寫出帶缺口的使用規格。決策齊備後，文件僅保留操作、版本、用途、前提、重要結果含義及補充限制；功能的參數來源及轉換留在 Spec；已拆分時歸 Design。
- Given B 明確要求先看契約草案，When 產出，Then 沿用相同核心結構，提供具體型別、驗證及錯誤候選，補必要副作用、冪等與並行限制；集中說明介面候選及防重期限等未決政策。
- Module Contract 清楚呈現模組職責與操作說明。已有契約保留引用與必要使用說明；不足處依呼叫條件、輸入參數、回傳結果、錯誤回應、執行限制的順序，僅補需要的小節。
- 局部缺口只補對應部分，已知事實與新介面提案保持可辨識。

**失敗判準**

- A 未訪談就交付帶缺口的規格、重建完整參數表或 Schema。
- 自行改 API。
- 把 409 等提案寫成既有結果。
- 略過內容衝突規則。
- B 只寫「依現有契約」或型別／錯誤全留待確認而沒有具體候選。
- 將未確認型別、期限或並行策略標為定案。

## 16：獨立生成一致性

**測試輸入**

**失敗判準**

- 已有完整契約仍逐節重複同一引用。
- 兩個操作都重新抄寫輸入表。
- 新操作只寫「依契約」而無定義。
- 混淆回傳結果與錯誤。
- 新增權限、儲存、重試或副作用。
- 使用抽象標題讓讀者無法定位呼叫方式。
- 殘留模板提示或訪談標籤。


## 24：單份規格與開發交接

**測試輸入**

使用[開發交接素材](handoff-fixture.md)的 requirements.md，明確呼叫 Skill 產出正式規格；不指定文件數量或設計方法。

**預期行為**

- Given 已確認的簡單統計功能，When 建規格，Then 交付一份包含行為、責任、契約、品質要求及驗收的 Spec，不強制 DDD 或設計模式。
- 三個既定模組責任與入口、格式、錯誤、數值及量測條件完整，沒有新增政策；不需要原對話才能理解。
- Given 相同輸入，When 分別使用改版前後 Skill，Then 比較實際資訊與閱讀成本；字數較少只有在重要條件未遺漏時才是改善證據。
- 獨立讀者能指出目的、完成條件、責任、失敗結果及量測方法；模型與真人閱讀結果分開記錄。

**失敗判準**

- 為簡單功能增加工廠、通用框架或無用途文件。
- 省略格式邊界、錯誤或責任。
- 捏造效能數字。
- 只能靠原對話補全決策。
- 以更短直接宣稱更好。


## 25：效能需求釐清

**測試輸入**

> $backend-spec-planner 請把以下需求整理成正式規格：既有報表匯出功能要支援比現在更多的資料，並做到效能最好。現有契約與責任不變，目前沒有提供資料量、完成時間、資源限制或量測環境。先釐清必要問題，不改程式。

**預期行為**

- Given 負載及目標缺失，When 評估，Then 先提出有理由的單一必要問題，逐步取得會影響設計的量測條件，不擅訂效能門檻。
- 有足夠條件後才比較適用方案；快取、並行或分批不能改動既有順序、一致性及責任。
- 效能結果與規格定義分開，缺少實際量測時不宣稱達標。

**失敗判準**

- 直接承諾效能最好。
- 自行設定秒數或容量。
- 只因資料量大就要求 DDD／微服務。
- 未釐清即新增快取或並行。


## 26：規格驅動實作與局部變更

**測試輸入**

將案例 24 的生成規格交給新的開發對話，明確授權在隔離範例實作與測試；不提供原始需求或評分判準。原版通過後，依[開發交接素材](handoff-fixture.md#規則變更)確認規格與 BDD 的變更，再執行第二階段。

**預期行為**

- Given 只有生成規格與必要契約，When TDD 開發，Then 有實際行為缺失造成的 Red、最小實作與 Green，語法或匯入錯誤不算 Red。
- 從 CLI 驗證正常、格式邊界、失敗與禁止副作用；從相同入口及環境量測記憶體峰值，保留實際數據及範圍。
- Given 已確認的新金額門檻，When 修改，Then 先改規格與相應情境，Red 揭露門檻缺失；產品程式的業務修改集中於 summary，不改讀檔與入口責任，受影響回歸通過。
- 規格、程式及測試各自評估；隔離範例通過不推論所有專案的品質或最佳效能。

**失敗判準**

- 開發時仍需猜測需求。
- 把匯入失敗當 Red。
- 以放寬測試通過。
- 統計規則散入讀檔或入口。
- 整檔載入造成線性記憶體增長。
- 只有單元測試或 exit code 就宣稱 BDD 完成。

**測試輸入**
