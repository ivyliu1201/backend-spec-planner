# 規格撰寫準則

操作流程見 [SKILL.md](../SKILL.md)；專業判準見 [DDD 設計](ddd-design.md)與[批次處理](batch-processing.md)。

## 完整性

- 兩種合理實作若會改變業務結果、介面行為、一致性、責任、權限或失敗後果，就補足約束；已有定義直接引用。
- 依業務用例組織。Spec 定義可觀察行為，Design 定義責任、互動與實作限制；等價的內部寫法保留彈性。
- 讀者須能理解功能目的、啟動條件、完成條件、主要限制與例外，並找到必要技術細節。
- 分清受理、處理完成與成功；非同步或部分失敗時，說明完成證據及最終結果的取得方式。

## 編排

- 章節依內容關聯與責任劃分。需一起判讀的內容可合併，例如輸入、輸出與完成條件；不同用途的內容分開，避免重疊定義。
- 標題簡短，清楚標示內容範圍。
- 功能開頭用短段落交代業務脈絡。條件與限制用列點，順序用步驟，平行比較用表格，必要的契約範例用程式區塊。
- 句子寫清主體、條件、動作與結果，補足重要例外及禁止副作用。術語首次出現且影響理解時簡短解釋。
- 將「適當處理」「必要時重試」改成可判定的條件與結果；缺少依據的門檻依主檔訪談處理。

## 依據

- 規則依使用者指示、適用規範與需求決策撰寫；程式及測試證明實作現況。新選擇或來源衝突依主檔釐清後再定義。
- 引用定位到文件章節、操作、Schema 或程式符號，附必要版本；同節共用來源集中列一次，個別差異就地補充。
- 正式文件直接陳述規定與理由，訪談過程留在對話。明確要求草案或審查時，依委託指出缺口。
- 保留來源原意與適用範圍；對話決策可記日期及摘要，示例使用虛構資料。

## 追溯

- 每項規則只在一處完整定義，其餘引用；既有 OpenAPI、Schema 或介面宣告沿用原定義。
- 業務規則採穩定識別碼與具名標題，例如 `BR-Q-001：同企業查詢`。沿用已有編碼；無編碼時補追溯索引，不重編或挪用既有識別碼。
- 重要引用附規則名稱，讓讀者知道引用的內容。
- 共用操作依 [Module Contract](../assets/templates/module-contract.md)記錄；功能的參數來源、轉換及回應用途歸 [Feature Design](../assets/templates/design.md)。

## 去重

Spec 各區塊的責任：

| 區塊 | 內容 |
| --- | --- |
| 業務規則 | 通用條件、結果及不變條件 |
| 處理流程 | 順序、交接與分支，引用規則 |
| 狀態轉換 | 允許的轉換與條件 |
| 驗收情境 | 以具體資料驗證正常、失敗與邊界結果 |

Design 的安排：

- 責任表定位規則擁有者與操作；領域模型補模型定義及一致性邊界。對應複雜且無法直接定位時，才補規則索引。
- 選用理由放在責任分工，局部限制的理由放在相關內容。跨多處的選擇或重要取捨可集中於「設計決策」，其他位置引用。
- 沿用既有設計時引用依據；省略獨立決策章節仍須保留重要理由、代價與約束。

精簡先刪重複與贅詞，保留條件、範圍、單位、失敗結果、責任及必要契約。已由敘述或表格說清楚的內容不再換形式重述。

## 驗收

- Given／When／Then 描述具體前提、實際入口的動作與可觀察結果，包含必要禁止副作用。
- 情境能獨立理解，規則引用只輔助追溯；覆蓋會改變結果的正常、失敗與邊界。
- 保持「規則／情境 → 責任 → 流程或操作」可追溯；情境定義與實際測試結果分開記錄。

## 核對

- 核對受影響的行為、責任、契約、失敗處理、品質要求及 BDD 是否相容；資訊不足與不適用須可區分。
- 相同需求與決策維持核心結構及重要結果一致。
- 行為變更沿「規則 → 情境／狀態 → 責任與契約 → 引用處」追查；功能特例標明適用範圍。
- 審查發現附位置、證據、影響與修正建議，依影響排序。
