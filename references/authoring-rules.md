# 規格撰寫準則

流程見 [SKILL.md](../SKILL.md)，設計判準見 [design-rules.md](design-rules.md)。

## 完整性

- 合理實作仍可能產生不同業務結果、介面行為、一致性、責任、權限或失敗後果時，補足約束。
- 說明目的、前提、輸入、輸出、完成條件及重要例外，保留等價內部實作的彈性。
- 非同步須區分受理、完成與成功，說明最終結果的取得方式；部分失敗須有明確判定。

## 編排

- 用詞適度、明確；標題標示單一主題，句子直接陳述規則。
- 並列條件優先列點，順序用步驟，比較用表格；背景或因果需要連貫說明時才用段落。
- 刪除贅詞、旁支解釋與重複提醒；不為補充說明引入無關概念。
- 保留主體、條件、動作、結果、單位及必要例外；避免只剩關鍵字。
- 術語首次出現且影響理解時簡釋；圖與範例按需使用。
- 模糊要求改為可判定條件；缺少影響驗收的依據時依主檔訪談。

## 依據

- 使用者決策與適用規範定義需求；程式及測試證明實作現況。新決策或來源衝突先釐清。
- 引用定位至章節、操作、Schema 或程式符號，附必要版本；共用來源集中一次。
- 正式規格記錄規定與設計理由；訪談、選項及當次執行階段留在對話。
- 對話定案須寫入正文或可取得的決策文件。保留來源範圍，示例使用虛構資料。
- 草案與審查明列缺口；未知事項不得寫成不適用。

## 去重

- 每項規則完整定義一次，其餘具名引用；既有 OpenAPI、Schema 或介面定義直接沿用。
- 正文使用具名規則與情境；必要的 AC01 等編號及「規則／情境 → 責任 → 操作／測試 → 證據」對照集中附錄。
- 正文僅在必要交叉引用或專案要求時使用編號；保留既有編號對應，不任意重編。無追溯需求不建立附錄。
- 規則定義條件與結果，流程補順序及交接；狀態表只補必要轉換。
- 理由留在相關設計；跨多處的取捨可集中，保留代價及依據。
- 功能參數來源、轉換與結果用途放在 Spec；設計拆分後歸 Design，擇一維護。共用操作另依 [Module Contract](../assets/templates/module-contract.md)。
- 品質目標及驗收方法由 Spec 定義；Design 只寫措施與取捨，共用操作限制引用契約。
- 異常對外結果由 Spec 定義，Design 說明處置流程；操作錯誤型別引用契約。

## 驗收

- BDD（行為驅動開發）以具體例子釐清需求，再以 Given／When／Then 記錄。
- 情境須經使用者確認，或對應使用者指定遵循的現行規格；模型推論不算確認。既有情境不重問。
- 覆蓋正常、失敗及邊界；寫出前提、實際入口、可觀察結果與禁止副作用。
- 情境須獨立可讀；相近輸入可用例表，規則引用不能取代預期結果。
- 情境與測試結果分開；執行證據連結實際紀錄。

## 開發交接

- 僅憑規格與引用資料即可找到行為、責任、契約及品質限制，不依賴原對話或 Skill。
- 指定驗收入口與方法；測試指令須有專案依據。
- 開發獲授權後，以確認情境進行 TDD（測試驅動開發）：有效 Red、最小實作、責任邊界內重構，再由實際入口驗證 BDD。純重構先驗證既有行為。

## 核對

- 核對行為、責任、契約、失敗處理、品質要求與 BDD 的一致性。
- 相同輸入應維持重要結果與責任一致，不要求字句或章節完全相同。
- 行為變更沿「規則 → 情境／狀態 → 責任／契約 → 引用」追查；特例標明範圍。
- 審查發現附位置、證據、影響與建議，依影響排序。
- 未執行的驗證標明限制；規格審查不能代替實作測試或效能量測。
