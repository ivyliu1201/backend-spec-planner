# 領域與模組設計

檢查模型、責任、協作與模式選用；撰寫準則見 [authoring-rules.md](authoring-rules.md)，變更授權見 [SKILL.md](../SKILL.md)。

## 領域邊界

- 從業務概念、操作與不變條件辨識領域，再對照既有模組。
- Bounded Context（限界上下文）界定術語與模型的適用範圍，明定資料、規則與變更權的擁有者。同名異義的概念須說明轉換關係。
- Context Map（上下文關係圖）以表格或簡圖呈現提供者、使用者、整合契約、資料方向及一致性責任。
- 領域邊界、程式模組與部署單位分別依需求判定，不預設一對一。

## 領域模型

依業務特性選用，並明定規則擁有者：

| 概念 | 適用條件 | 必要內容 |
| --- | --- | --- |
| Entity（實體） | 持續識別同一業務對象 | 身分、生命週期、可變狀態與操作權限 |
| Value Object（值物件） | 由值及有效性決定意義 | 相等條件、單位、精度、有效值與不可變要求 |
| Aggregate（聚合） | 共同維護一致性邊界 | 不變條件、修改入口、原子更新範圍與跨邊界協作 |
| Domain Service（領域服務） | 規則跨對象，缺少自然持有者 | 規則、輸入與結果，以及既有對象無法承擔的原因 |

- 聚合範圍由一致性需求決定，須考慮大批次的載入與更新成本；跨聚合的原子性或最終一致性依業務結果與既有能力決定。
- 使用既有名稱定位責任：Application 協調用例與交易；Domain 維護規則及狀態轉換；Infrastructure 實現持久化、傳輸與檔案操作。
- 例如「受理後不能更換原始內容」，需定義受理狀態、不可變範圍及維護者。

## 模組選用

- **協作**：不同模組完成不同責任，說明交接資料、順序、成功／失敗回應及後續動作的決定者。
- **替代**：相同能力依資格條件、互斥條件或優先順序選用，並指明條件來源與選擇責任。
- **符合數量**：零個時依規則拒絕、轉人工或採替代途徑；一個時核對契約；多個時依決勝規則。缺少選用依據時，依主檔訪談。
- **失敗切換**：另定義可切換條件及副作用防重，不能直接沿用初次選用規則。

## 設計模式

- 先辨識變化點或耦合問題，再比較候選模式、直接實作及既有元件，評估收益與維護成本。
- 採用時說明參與責任、協作方式、使用時機與限制，並核對公開契約、狀態及一致性的影響。
- 下表為候選示例；依問題選用，也可採表外模式或不增加模式。

| 問題 | 候選示例 | 必要約束 |
| --- | --- | --- |
| 建立方式有差異或需維護多項條件 | Factory Method（工廠方法）、Abstract Factory（抽象工廠）、Builder（建造者） | 建立與選擇責任、輸入、有效性、生命週期及失敗結果 |
| 介面／模型不相容或需要集中入口 | Adapter（轉接器）、Facade（外觀） | 轉換規則、簡化範圍、錯誤含義、依賴方向及原有規則歸屬 |
| 演算法可替換或流程部分步驟不同 | Strategy（策略）、Template Method（樣板方法） | 變化點、選用條件、固定部分及組合／繼承限制 |
| 行為隨業務狀態改變 | State（狀態） | 合法轉換、規則來源、轉換責任、禁止操作及結果 |
| 請求封裝、處理者協作或事件通知 | Command（命令）、Chain of Responsibility（責任鏈）、Observer（觀察者） | 與問題的對應、執行時機、處理者選擇、順序、繼續條件及失敗責任 |
| 組合額外行為或處理層級物件 | Decorator（裝飾者）、Composite（組合） | 組合順序、相容性、個體／整體行為、不變條件及依賴成本 |

交易、冪等、非同步與撤銷等保證須有具體契約依據，不能由模式名稱推定。

## 設計檢查

- **責任**：先描述模組能力、公開介面與依賴，再展開有歧義或高風險的內部區段。
- **互動**：正常及重要失敗路徑涵蓋呼叫者、操作、輸入來源與結果；狀態變更及副作用須對應具體操作與契約保證，缺少必要能力時依主檔訪談。
- **共用約束**：交易、安全、時間及錯誤分類引用既有定義，只補功能差異。
- **決策**：保留重要選擇的理由、代價與依據；編排依[去重準則](authoring-rules.md#去重)。
